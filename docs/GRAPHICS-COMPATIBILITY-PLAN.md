# 受限 Vulkan 驱动的图形兼容计划

目标是在不修改游戏文件的前提下，让桌面 OpenGL 绘制能够使用功能较少的 Android Vulkan 驱动。兼容性按实际驱动能力和渲染结果验证，不按设备型号、游戏版本或引擎文件哈希划定范围。

## 已确认的问题

- 游戏的当前绘制路径使用 OpenGL；dynamic rendering 是现用 Zink 转换实现的要求。
- 将 Mesa 从 26.3 换成 26.1 不能补齐 `VK_KHR_dynamic_rendering` 和 robustness2 的缺口。
- Vulkan 实例创建成功不等于 Zink、OpenGL 上下文或游戏画面成功。
- 初始化失败后的进程清理可能产生 137；须保留原始错误和主动终止记录，不能据此推断 OOM。
- 当前 Mesa 的部分必需扩展错误使用 release 构建会移除的调试输出，诊断需要补足这一层。

## 执行顺序与验收

| 顺序 | 方案 | 执行内容 | 验收与后续条件 |
| --- | --- | --- | --- |
| 0 | 清理无效设置 | 移除 Mali 兼容开关、偏好读取、跨进程参数、状态和相关文案；保留诊断及已有有效渲染修复 | 构建、主机回归通过；旧偏好不再影响运行库；前台和接收端仍选择一致的运行库 |
| 1 | 保留回退路径的 Zink | 首先审核 Mesa 23.1 的传统 render pass、传统描述符和现有 WSI 接口；独立构建并在诊断进程中验证，避免直接替换已有工作路径 | 依次通过 Vulkan 查询、EGL 初始化、游戏所需 OpenGL 上下文、绘制/纹理/混合小探针、真实游戏主菜单与地图；记录实际错误后再决定是否继续使用该版本 |
| 2 | 调整兼容版 Zink | 第一方案若受可定位的旧版问题阻碍，回移必要修复，或将传统 render pass / 描述符实现移植到较新版本 | 为每项改动保留可复现探针；不能只删除功能检查或虚报 Vulkan 特性；同时回归已有可运行的渲染路径 |
| 3 | 局部 Vulkan 功能转换 | 在 Zink 与 Vulkan ICD 之间实现 dynamic rendering 到传统 render pass 的转换；独立评估空描述符语义 | 处理管线兼容性、附件、清除/保存、同步、次级命令缓冲及生命周期；先限定并验证实际实现范围，再公布支持能力 |
| 4 | 其他驱动或渲染实现 | 评估能够匹配现有内核接口的替代驱动，或另一条具备游戏所需 OpenGL 功能的硬件加速路径 | 先确认内核/用户态 ABI、呈现与必要功能；不将系统改造作为普通用户默认安装步骤 |

每一级先执行能够独立验证的最小实验。低一级方案只在前一级出现已定位障碍、收益不足或维护成本不可接受时展开。找到能正确运行的路径后，先完成该路径的集成与回归，不同时铺开多个未经验证的用户选项。

## 第一方案的源码依据

Mesa 23.1 的 `zink_context.c` 在没有 `VK_KHR_dynamic_rendering` 时调用 `zink_begin_render_pass()`。同版 `zink_screen.c` 在缺少 `nullDescriptor` 时能够放弃 descriptor-buffer 模式，自动模式可选择传统描述符路径。这证明旧实现具有可评估的回退逻辑，不代表它已通过整个游戏的运行验证。

## 构建与验证边界

- GNU Mesa provider 可使用 macOS/Linux 的交叉编译环境构建；安卓 APK 在 Windows 构建。
- 实验运行库单独存放，确认兼容性前不覆盖当前使用的 provider，也不添加承诺修复效果的用户开关。
- 自有补丁、构建输入、命令和依赖来源必须可从源码还原；预编译文件只作缓存。
- 设备连接参数只在命令中传入；设备会话日志作为诊断产物保留，不写入通用源码和用户文档。
- 实机验收同时检查日志、真实出帧和可见画面；继续验证贴图格式、透明混合、地图加载和退出。

- 恢复正常压缩配置后，真实游戏画面恢复，用户已确认画面正常。自动能力查询、运行库选择和 APK 载荷集成已通过 Windows release/debug 构建、格式检查与 8 组主机回归；APK 中五个传统 provider 的载荷检查通过。删除设备上的实验选择后，实际启动已自动使用 APK 内的传统运行库，OpenGL 初始化与 GPU 压缩自测通过。

## 结论：原因与修复方法

本次有两个阶段的问题。首先是初始化失败：较新的 Zink 依赖驱动未提供的 dynamic rendering 和空描述符能力；游戏使用 OpenGL，并没有直接要求这些 Vulkan 特性。降低游戏画质或在两套都要求这些特性的较新 Mesa 之间切换，无法修复这个缺口。采用仍保留传统 render pass 和描述符路径的 Mesa 23.1.9 后，可以使用现有 Vulkan 驱动完成绘制，无须修改游戏或系统驱动。

其次是初始化成功后的画面错误。旧版适配需要修复呈现模式选择、窗口颜色格式和 WSI 图像用途协商；这些分别影响交换链创建、红蓝通道和附件用途。其中地板缺失、条纹及移动物体残影的直接原因，是旧 Zink 的缓冲纹理视图上限计算发生整数溢出：

```c
// 原实现：两个 32 位值先相乘，溢出后才赋给 64 位变量。
uint64_t clamp = blocksize * maxTexelBufferElements;
// 修复：从乘法开始就使用 64 位整数。
uint64_t clamp = (uint64_t)blocksize * maxTexelBufferElements;
```

例如每纹素 16 字节、驱动最大纹素数为 268435456 时，乘积为 2^32，原计算会变成零。完整缓冲视图因此被错误裁成零长度，地形顶点着色器无法读到遮罩坐标；地面未正常重绘，也会让运动物体看起来留下上一帧。较短的缓冲视图没有触发同一裁剪分支，所以单纯验证纹理上传、混合或部分范围绑定会漏掉该问题。

修复回移较新 Mesa 已采用的 64 位计算，不降低驱动上限，不改变 `VK_WHOLE_SIZE` 语义，也不虚报 Vulkan 特性。完整缓冲、显式整段、短范围及偏移范围的 12 项 MRT 像素对照通过；恢复正常压缩配置后的真实游戏画面也已确认正常。关闭压缩和强制同步均未解决问题，已撤销这些实验参数。这里的证据支持已验证场景的正确性，不能据此宣称所有驱动、全部 OpenGL 功能或长时间地图压力测试均已通过。

正式集成按实际 Vulkan 功能自动选择运行库：已确认缺少 dynamic rendering 或 nullDescriptor 时使用传统路径，能力足够时保留原有路径，查询失败时也保留原有选择并记录诊断。移除无效的 Mali 兼容开关，不要求玩家自行猜测。五个传统 Mesa provider 随 APK 打包；公开源码、工程补丁、构建命令及缓存校验流程见 [源码构建说明](../native-input/mesa-legacy/README.md)。运行库构建缓存的哈希只用于确认产物对应当前源码和补丁，不参与游戏版本或设备准入。
